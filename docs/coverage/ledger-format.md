# Coverage ledger format

These artifacts are a source-anchored structural inventory for the pinned Core revision. They are discovery aids for the per-domain contract ledgers; they do not establish that a declaration is present in the shipped archive or that its runtime behavior is known.

## Header inventory (`docs/core-header-inventory.csv`)

The original source identity columns (`upstream_header`, `source_sha256`, installed-header state, and installed-byte comparison) remain unchanged. The `classification` vocabulary is `public functionality`, `event`, `setting`, `internal helper`, `dependency detail`, or `platform-specific implementation`. `classification_rationale` explains the role from header contents and source context; filename alone is insufficient evidence.

`capability_ids` is a JSON array of stable domain identifiers. Current identifiers are: `lifecycle`, `settings`, `logs`, `crypto`, `geo`, `connection`, `connectivity`, `hub`, `protocol`, `search`, `private-chat`, `favorites`, `ignore`, `recents`, `viewed-files`, `user-commands`, `activity`, `common-core`, `util`, `queue`, `download`, `upload`, `transfer-info`, `filelist`, `hash`, `share`, `share-profiles`, `temp-share`, `modules`, `updater`, and `platform`. A source header may have more than one owner when its declarations cross domain boundaries. Internal/dependency/platform rows still retain relevant owner IDs for traceability and do not imply public bridge capability.

`source_evidence` is a JSON array of exact source anchors with `path`, inclusive `start_line`/`end_line`, `symbol`, and `kind`. Anchors are representative structural evidence, not an exhaustive list of every declaration; `declarations.json` is the declaration-level index. Existing `availability`, `operation_inventory`, `bridge_api`, `tests`, and `example_scenario` columns remain separate: structural classification does not fill in semantic or implementation status.

## Declaration index (`docs/coverage/declarations.json`)

Schema version 1 records declarations with stable IDs, kind/name/signature, a source reference, source text, extraction method, access information when available, domain ownership, header classification, source/install availability, and `structural_only: true`. `source_ref.path` is relative to the pinned source root `airdcpp/`; line numbers are one-based and inclusive. Overloads remain separate records by source location and signature. The index intentionally distinguishes:

- `extraction_kind: libclang`: a declaration observed in the Xcode libclang C Index traversal under the recorded C++20 macOS host arguments. This is compiler-parsed evidence for that translation unit only.
- `extraction_kind: lexical-source`: exact source-spelled declarations from a dependency-blocked header (`ZipFile.h`), whose external minizip types prevent compiler validation.
- `extraction_kind: macro-invocation`: a source macro invocation retained at its call site. The record documents the expansion shape from `core/types/GetSet.h`; generated accessors have no independent source-spelled signature location and are not represented as compiler cursors.
- `extraction_kind: lexical-conditional-region`: complete source intervals for every non-include-guard conditional branch, including full nested/alternative predicates. These source intervals account inactive code without asserting individual declaration typing or branch truth.
- `extraction_kind: lexical-conditional`: exact source lines under platform/build preprocessor conditions not active in the host parse. `condition_stack` records the source condition expressions; grouping, branch truth for another target, access and type semantics are not inferred.

The pinned snapshot has 245 installed headers and 18 source-only headers: 17 optional-module headers and `ZipFile.h`. The current AST unit reaches 262 of 263 pinned headers. `StringDefs.h` is parsed transitively in its intended `ResourceManager.h` class context rather than included as a standalone header. `ZipFile.h` is lexical-only because its external `minizip/unzip.h` dependency is absent from pinned source dependencies and installed distribution headers. Platform-specific/inactive source lines are retained lexically where detected, while `source_surface_gaps` explicitly records the remaining limits. Host parsing does not reproduce every CMake feature macro, Windows target, or distribution preprocessor configuration. No completeness claim is made for inactive branches, archive symbol availability, implicit/generated declarations beyond recorded macro expansions, or compiler semantics on another target.

`access` reports Clang's declaration access where available. Macro expansion can change access for following declarations: the generated accessor macros switch visibility to public after emitting protected storage, so AST access is retained and macro invocations are separately anchored. A lexical record whose access is `conditional-context-not-parsed`, `source-context-not-parsed`, or `macro-dependent` must not be interpreted as an API visibility determination.

## Source accounting (`docs/coverage/source-accounting.json`)

Schema version 1 has `files` records for 146 tracked `.cpp`/`.c` translation units and one separately labeled observed generated translation unit (`StringDefs.cpp`). Each record contains `path` relative to the source root, SHA-256 of pinned source bytes, `kind`, one or more `domain_ids`, and a `classification_rationale`. Recognizable listener, setting-default, module, and related registration calls are attached as `sites` arrays with one-based `line`, `kind`, and exact source text excerpt. A site is discovery evidence and does not claim semantic completeness. The ledger contains 147 observed translation units and source-line registration references for focused follow-up by domain owners. `StringDefs.cpp` records its pinned generator/header/build-rule provenance; its observed hash is not called a tracked source identity. `generated_inputs` separately binds checkout `version.inc` and accepted distribution version bytes, their differing values and the Project 1 deterministic private-stage authority. The framework consumes the accepted distribution, whose version tag is 0.0.0 and build count 0; the ignored checkout output has an empty tag and count 1. Byte hashes remain authoritative when source excerpts require text decoding.

The source pin is `55d51ceb817ec006d4ec844d9e3788e1b0ccc352`. Header declarations, source translation units, binary/archive symbols, runtime behavior, and generated configuration are distinct evidence layers; one does not prove another. Domain operation ledgers own behavioral claims and acceptance scenarios. This structural layer must not be used to infer successful initialization, ownership/lifetime, threading, event ordering, defaults, errors, completion/cancellation, persistence, or prerequisites.

## Domain contract ledgers (`docs/coverage/domains/*.json`)

Each schema-version-1 document binds its `domain_id` and `upstream_commit` to the same pinned source. Stable record IDs identify semantic families; they need not equal individual C++ declaration IDs. A family may group related overloads, model members, generated string constants, or internal implementation state when its rationale preserves their role. Grouping does not exempt externally meaningful behavior from a concrete source contract.

Records retain exact `upstream_symbols`, bounded `source_refs`, source/installed/compiled `availability`, and `behavior` (inputs, preconditions, defaults, effects, events, errors, completion, cancellation, persistence and resources). Ownership and threading evidence remain separate. `surface_classification`/`surface_rationale` distinguish bridge functionality from helpers and implementation details; C++ public access alone does not establish a standalone bridge capability.

Structural links currently use `declaration_ids`, `structural_declaration_ids`, or the single-value `structural_declaration_id`. Validation takes their union and reconciles it with the indexed declarations owned by the domain. These are equivalent mapping representations, not different levels of coverage. `structural_members` may preserve exact source text for grouped members. Overlapping links across concrete contracts are allowed when the behaviors overlap; record IDs must remain globally unique.

`acceptance_scenarios` contains complete Given/When/Then strings or objects with `given`, `when` and `then` keys. Capability scenarios describe concrete input states and observable outcomes. Internal-only families may instead have no scenarios and an explicit exclusion rationale. Generic eventual-fixture or unread-source placeholders are discovery records and cannot pass the semantic gate. Scenarios are future characterization requirements, not passing runtime tests. A setting contract may reference a stable, source-backed operation ID for downstream behavior instead of duplicating its workflow. It still states known type/default/unit/normalization/persistence and a meaningful concrete fixture. Remove redundant generated predicate cases rather than asserting that an unspecified true condition enters a branch; this inventory does not require exhaustive combinations of every consumer predicate.

`status: inventoried` records source-contract discovery. `contract_evidence: source-traced`, where present, distinguishes inspected bodies without changing the controlled implementation status vocabulary. Neither means the Objective-C API has been approved or implemented. Until later gates, `bridge_api` and `example_scenario` may remain null and `implementation_tests` empty. Compiled/runtime availability remains unverified with a defined `gap_ids` reference; disabled or platform-specific functionality remains explicit rather than being counted as implemented.
