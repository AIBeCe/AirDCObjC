# Core integration contract

## Inspected baseline

- Distribution project: AirDCCore-macOS v1.0.0.
- Original Core repository: https://github.com/airdcpp/airdcpp-core
- Core commit: `55d51ceb817ec006d4ec844d9e3788e1b0ccc352`.
- Aggregate archive: `Dist/lib/libairdcpp.a`.
- Aggregate SHA-256 observed in manifest: `3e6b1d2be3e7d29e80b19a38633df7d3c9229730f25f1a50abf4f64b588462bb`.
- Policy: ARM64, Release, static Core, libc++, C++20, macOS 14.0.
- Private consumer include roots: `include` and `include/airdcpp`.
- Required private definition: `NO_CLIENT_UPDATER`.
- Explicit system library: SDK Iconv; implicit libraries: libc++ and libSystem.
- Existing Core link interface declares no Apple frameworks. The Objective-C framework itself will additionally use Foundation.

The checksum above is an inspected manifest claim, not a checksum freshly regenerated by this documentation task. Acquisition must independently verify actual archive and header bytes against accepted provenance.

## Containment

AirDCObjC links the aggregate once into its dynamic framework. Igualada must not separately link another copy of Core. Verify dependency load commands, C++ exports, symbol collisions, deployment platform, and real force-loaded link closure.

Public framework headers contain only bridge-owned declarations. Private build inputs may include the verified Core and dependency headers. They must never depend on sibling `Build` directories, Homebrew libraries, or undocumented developer paths.

The dependency input consists of archive, headers, metadata, checksums, and licenses together. Version the acquisition policy and exact release/source identities; keep acquired bytes and build products generated. No submodules are required by the approved direction.

## Platform and feature limitations

Current build disables NAT-PMP and TBB. Optional Core modules default off on non-Windows. Upstream omits updater downloader/updater implementation and Windows UPnP/ZIP implementation on non-Windows. TBB is an execution/performance option; it does not itself define a user-facing feature.

Record each resulting functional gap in the coverage ledger. Feature availability is established by configuration and actual compiled symbols/behavior, not merely installed headers.

## Runtime resources

Determine certificates/trust configuration, OpenSSL configuration/provider paths, localization, GeoIP database, storage databases, logs, and module resources by tracing original Core behavior. Define host configuration and ownership explicitly. The Core archive does not automatically supply all runtime data.

Do not embed credentials or host-specific paths into published artifacts or example fixtures. Storage migration and profile compatibility require reviewed tests before changing persisted formats.

## Upstream change control

A new pin requires a header/API/event/settings diff, coverage updates, adapted tests, source/provenance review, and compatibility verification. Never claim parity against a moving upstream branch.

Keep source references reproducible at the pinned commit. Platform repairs belong in a separately approved Core change if they affect its distribution; do not hide repairs inside copied headers or patch acquired binaries.

## Attribution and source provenance

Preserve the Core's GPL-3.0-or-later notices and all dependency license texts, notices, and source identities. Distribution documentation must explain artifact/source provenance and include the materials required by the selected release policy. No release policy or licensing interpretation is established by this design-only task.
